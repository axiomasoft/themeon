## 1. Context

ThemeOn — экстракция самодельного паттерна темизации, скопипасченного минимум в 3 проектах
(dterema/vintera/octoclick), в универсальный OSS-пакет: типизированные TS-токены →
CSS custom properties (build+runtime) → адаптеры UI-библиотек (Naive UI первым) +
CSS-фундамент (@layer, reset, layout-примитивы). Ниша валидирована RAG: прямого
конкурента нет (ближайший TokiForge — без адаптеров к компонентным библиотекам).

**Дизайн-обоснования и решения D1–D17 — `00_MASTER_PLAN.md` (этой папки), читать при
любых сомнениях в «почему». Research-база: `20_research/R-01..R-07` (RAG 2026-07-07).**

## 2. Execution Rules

- Один item за раз; статус обновляется В ПЛАНЕ до завершения работы.
- Статусы — 6 канонических строк (plan-protocol §5).
- План разошёлся с кодом/фактами → эскалировать, не импровизировать.
- После закрытия item/фазы — перезаписать `plans/THEMEON/handoff.md` целиком.
- Решения D1–D17 (`00_MASTER_PLAN.md` §5) не пересматривать молча; изменение — новым D#.
- Внешние факты (версии, API) — только RAG с URL; без источника — `[UNVERIFIED]`.
- Код: комментарии/тест-описания на русском (`general:writing-style`); публичные README/JSDoc пакета — английский (OSS).
- Vault-файлы этой папки — источники, НЕ артефакты исполнения; код живёт в `~/projects/packages/themeon`.
- Пилоты (P5) трогают прод-проекты dterema/vintera → перед миграцией фиксировать diff генерируемых CSS-переменных (обязан быть пустым при `aliases: legacy-v0`).

## 2а. Design Program — протокол пофазной детализации (утверждено пользователем 2026-07-07)

Сегодняшний план — каркас. Каждая фаза разворачивается в **отдельной сессии с чистым
контекстом** до состояния, при котором исполнение НЕ требует дизайн-модели — исполнитель
(sonnet) не принимает ни одного самостоятельного решения:

1. **Одна сессия = одна фаза.** Вход: `/task:plan-design THEMEON P<n> --from plans/THEMEON/plan.md` (новая сессия, чистый контекст).
2. **Модель — по риску фазы, см. §3 Routing «Design-стадия по фазам»** (пересмотр 2026-07-12
   P-D17; 2026-07-13 P-D32: fable удалена, верх шкалы — opus/xhigh. Canon [feedback: No Model
   Economy in Design] остаётся в силе там, где ошибка дизайн-стадии дорога — не отменяется
   поголовно, а адресуется по фазе).
3. **Углублённый research через perplexity-web ОБЯЗАТЕЛЕН** на каждую фазу: точечные вопросы фазы (API конкретных библиотек, edge-cases, свежие релизы) — результат в `20_research/R-1x_P<n>-*.md` с URL. R-01..R-07 не переделывать — только углублять.
4. **Definition of Detailed** для `phases/P<n>.md` — исполнителю (sonnet) не нужно ничего решать:
   - полная файловая структура затрагиваемых пакетов (дерево);
   - сигнатуры публичного API (TS-интерфейсы целиком) и куски эталонного кода для нетривиальных мест;
   - схемы данных/алгоритмы словами + примеры вход→выход;
   - референсы (URL + конкретный файл/строки чужого кода, если паттерн заимствуется);
   - критерии приёмки и шаги верификации per item;
   - явные не-цели фазы.
5. После детализации фазы — обновить Status Board здесь + перезаписать `handoff.md` (в конце — команда запуска следующей сессии).
6. Исполнение кода (`/task:plan-exec` / `/task:dev`) начинается только после детализации соответствующей фазы; сегодня код не пишем.

## 2б. Автоматизация фаз (workflow-скрипты, добавлено 2026-07-08; P5 — 2026-07-13)

Альтернатива ручным сессиям §2а — три Workflow-скрипта в `plans/THEMEON/workflows/`:

- **`themeon-phase-dev.js`** — вызывается ОТДЕЛЬНО на каждую фазу (`args: {phase: "P1"}`, НЕ
  автопрогон P1→P7 разом — item'ы одной фазы исполняются строго последовательно, общий репо).
  Стадии: Status → (если фаза не детализирована) Research (perplexity-web,
  `20_research/R-1x_P<n>-*.md`) → Design (модель по §3 Routing «Design-стадия по фазам»,
  Definition of Detailed) → на каждый item:
  Implement (модель по §3 Routing ниже; сам пишет файлы и коммитит) → Review (opus/xhigh,
  adversarial по коммиту) → Fix (sonnet/medium, только если находки MED+) → Close (sonnet/low,
  независимая сверка по git-фактам) → Wrap-up (закрытие фазы, handoff.md, Update Log).
  **P0 и P5 исключены** (P0 сделана вручную; P5 — свой скрипт, см. ниже).
- **`themeon-p5-pilots.js`** — только фаза P5 (пилоты), потому что она единственная мутирует
  ЧУЖИЕ прод-репозитории (`~/projects/dterema/app`, `~/projects/vintera/vintera`), а не сам
  пакет. Три защиты, которых нет в общем phase-dev (P-D33):
  **(1) Preflight** — working tree обоих пилотов обязан быть чист; скрипт НИКОГДА не делает
  `git stash`/`reset`/`checkout -f` в чужом репо, грязно → стоп с инструкцией.
  **(2) Ветка** `themeon-migration/P5` от текущего HEAD пилота — вся миграция коммитится
  только туда, БЕЗ push и БЕЗ merge (merge в основную ветку прод-проекта делает человек).
  **(3) Parity-гейт** — обязателен по §2 Execution Rules и D5/D17: Baseline снимает множество
  генерируемых CSS-переменных ДО миграции пилота, Parity пересравнивает ПОСЛЕ каждого item'а;
  непустой diff (кроме явно санкционированных планом переменных — напр. починка `--size-2-xl`)
  = регрессия прод-стилей → фаза стопается.
  Стадии: Preflight → Research → Design (opus/xhigh) → на каждый item: Baseline (1× на пилота)
  → Implement (sonnet/medium, коммит в ветку) → **Parity** → Review (opus/xhigh, adversarial:
  визуальная регрессия/FOUC/SSR — то, что parity по переменным поймать не может; обязателен
  по §3 Routing) → Fix → Close → Wrap-up (+ готовые команды ручного merge).
  `args` опциональны: `{onlyItems: ["P5.1"]}` — подмножество item'ов; `{planDir: "..."}`.
- **`themeon-final-audit.js`** — БЕЗ args, разовый запуск после того как нужные фазы
  терминальны. Recon (sonnet/low, сырые git/plan факты) → 4 параллельные opus-линзы
  (architecture/D1–D17 · phase-facts (adversarial git-аудит, xhigh) · oss-readiness ·
  security-integrity (xhigh)) → Verify (opus/xhigh опровергает HIGH/CRITICAL) → Synthesis
  (opus) → отчёт `plans/THEMEON/90_audit/FINAL_AUDIT_<дата>.md` с вердиктом GREEN/ATTENTION/RED.

Запуск (из чата, Sonnet-сессия — модель самой сессии не важна, стадии пинуют модели
внутри скрипта): «Запусти workflow plans/THEMEON/workflows/themeon-phase-dev.js на фазу
P<n> (Workflow tool, scriptPath, args: {phase: "P<n>"})»; для P5 — тот же паттерн с
`themeon-p5-pilots.js` (args не обязательны), для аудита — без args.
