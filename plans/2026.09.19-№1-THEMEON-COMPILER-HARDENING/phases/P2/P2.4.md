### P2.4 — API reports and TypeScript compatibility fixtures

**Intent:** Make declaration/public-surface changes reviewable and prove supported TypeScript call sites across root and subpath APIs.

**Why:** Runtime parity does not catch accidental type widening/narrowing or export drift.

**Scope Included:** Reuse check; per-package API declaration reports; approved baseline; positive/negative compile fixtures; CI diff artifact.

**Scope Excluded:** Semver automation; source ABI promises for private paths; public removal.

**Inputs:** `phases/P1/P1.6.state.md`; `phases/P0/P0.5.state.md`; `phases/P2/P2.3.md`; `phases/P2/P2.3.state.md`; `packages/core/package.json`

**Files:** `etc/api/**`; `tests/types/**`; API-report config/scripts; CI workflow; package build configs if required.

**Required Reads:** `plan.md`; `phases/P2/P2.md`; `phases/P2/P2.3.md`; `phases/P2/P2.3.state.md`; `packages/core/package.json`; `packages/core/src/api.test.ts`; `packages/cli/src/api.test.ts`; `packages/vite/src/api.test.ts`; `findings/audit-verdicts.md`

**Implementation Rules:** Reports cover only intended public entrypoints; baseline updates are human-visible; negative fixtures assert expected compiler codes where stable.

**Code Guidance:** Compile against packed declarations; keep fixtures consumer-shaped; separate formatting churn from semantic report changes.

**Validation:** Clean API report; deliberate public signature change causes diff; all positive/negative fixtures behave as expected; pack/build/typecheck green.

**Deliverables:** API baselines, compatibility fixtures, reviewable diff command and CI gate.
