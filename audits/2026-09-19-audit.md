Архитектуру ThemeOn **не следует переписывать с нуля**: пакетные границы, zero-dependency core, интеграционные тесты и разделение framework-адаптеров уже заметно лучше среднего pre-1.0 проекта. Главный следующий шаг — превратить набор сильных функций в **формально описанный компиляторный pipeline с независимой внутренней моделью, диагностикой и расширениями**, одновременно закрыв DTCG-совместимость, WCAG, безопасность публикации и контрактные тесты.

Ниже — первая глубокая итерация аудита. Она охватывает структуру репозитория, публичные контракты и ключевые файлы; это еще не буквальный построчный review всех примерно 150 коммитов и каждого исходника.

## Главная рекомендация

ThemeOn должен позиционироваться не как еще один Style Dictionary и не как UI kit, а как:

> **Typed theme compiler and runtime interoperability layer for TypeScript applications.**

У него должны быть четыре явные сущности:

1. **Authoring model** — удобный типизированный TS DSL.
2. **Canonical IR** — внутренняя модель, независимая от TS DSL, DTCG, CSS и фреймворков.
3. **Compiler pipeline** — normalize, validate, resolve, transform, emit.
4. **Runtime layer** — применение уже скомпилированного результата, а не повторная реализация компилятора в браузере.

Сейчас эти возможности фактически существуют, но распределены между `define.ts`, `resolve.ts`, `serialize.ts`, `apply.ts`, DTCG-модулями и CLI. В core уже сосредоточены authoring, resolver, serializer, runtime applier, tenant patches, JSON Schema, naming и DTCG interchange; это сильный функциональный набор, однако публичная точка входа постепенно становится фасадом сразу нескольких подсистем. [Публичный API core](https://github.com/axiomasoft/themeon/blob/main/packages/core/src/index.ts)

## Внутренняя модель

Сейчас `Token.path` одновременно выступает структурным положением, именем и фактической идентичностью. Это удобно в v1, но затрудняет source maps, rename migrations, диагностику коллизий и сохранение DTCG metadata.

Предлагаемая IR:

```ts
export interface TokenNode {
  readonly id: TokenId
  readonly path: TokenPath
  readonly type: TokenType
  readonly value: TokenValue
  readonly references: readonly TokenReference[]
  readonly metadata: TokenMetadata
  readonly source?: SourceLocation
}

export interface TokenMetadata {
  readonly description?: string
  readonly deprecated?: boolean | string
  readonly extensions?: Readonly<Record<string, unknown>>
  readonly original?: unknown
}
```

`id` необязательно должен быть пользовательским UUID. На первом этапе это может быть внутренний deterministic ID, вычисляемый из source namespace и path, но весь pipeline не должен считать CSS-имя идентичностью токена.

### Необходимые инварианты

- Authoring model никогда не зависит от CSS.
- IR никогда не содержит DOM-объекты.
- Naming выполняется после разрешения структуры.
- Formatter не изменяет IR.
- Runtime не разрешает token graph повторно.
- Adapter получает immutable compiled representation.
- DTCG importer не создает CSS-specific значения.
- Все потери данных при импорте/экспорте превращаются в diagnostics.
- Каждый output содержит fingerprint входов и compiler version.
- Один и тот же вход с одинаковой конфигурацией дает byte-identical output.

## Compiler pipeline

Лучшее, что стоит заимствовать у Style Dictionary, — не его API или конфигурационный формат, а последовательную архитектуру: поиск и parsing источников, merge, preprocessors, transforms, resolution и formats. Style Dictionary отдельно поддерживает preprocessors над всем словарем, platform transforms, filters, formats и actions. [styledictionary](https://styledictionary.com/info/architecture/)

Для ThemeOn pipeline может быть более строгим:

```text
load
  → parse
  → normalize
  → merge
  → validate-structure
  → build-reference-graph
  → validate-semantics
  → resolve
  → transform
  → validate-output
  → emit
```

Не следует копировать глобальный mutable registry Style Dictionary. Лучше сделать plugin registry scoped на один compiler instance:

```ts
export interface ThemeonPlugin {
  readonly name: string
  readonly version: string
  readonly apiVersion: 1
  setup(api: PluginApi): void | Promise<void>
}

export interface PluginApi {
  addParser(parser: Parser): void
  addNormalizer(normalizer: Normalizer): void
  addValidator(validator: Validator): void
  addTransform(transform: Transform): void
  addFormat(format: Format): void
}
```

Каждый extension point должен декларировать:

- Стадию выполнения.
- Какие части IR он читает.
- Какие части IR может изменять.
- Детерминирован ли результат.
- Cache key.
- Поддерживает ли async.
- Может ли выполняться параллельно.
- Какая версия plugin API требуется.

Асинхронные hooks полезны для расширяемости, но сетевой доступ во время обычной сборки лучше запретить по умолчанию. Style Dictionary уже движется к async preprocessors и hooks; ThemeOn может предусмотреть это сразу без глобального состояния. [github](https://github.com/style-dictionary/style-dictionary/blob/main/CHANGELOG.md)

## DTCG-совместимость

DTCG 2025.10 — теперь стабильный vendor-neutral формат, но он остается Community Group specification, а не W3C Recommendation. Спецификация определяет JSON interchange format, token/group distinction, `$type`, `$description`, `$extends`, `$deprecated` и наследование типа группами. [designtokens](https://www.designtokens.org/TR/2025.10/format/)

Публичная модель ThemeOn сейчас описывает десять core types и собственный composite `text`; metadata вроде description, deprecated, extensions и source information в основном `Token` type не представлена. [Типы core](https://github.com/axiomasoft/themeon/blob/main/packages/core/src/types.ts)

### Нужна формальная матрица

Создайте `docs/standards/dtcg-2025.10.md`:

| Возможность | Import | Preserve | Validate | Export | Lossless |
|---|---:|---:|---:|---:|---:|
| `$value` | Да | Да | Да | Да | Да |
| `$type` |  |  |  |  |  |
| Group type inheritance |  |  |  |  |  |
| `$description` |  |  |  |  |  |
| `$deprecated` |  |  |  |  |  |
| `$extends` |  |  |  |  |  |
| `$extensions` |  |  |  |  |  |
| Aliases |  |  |  |  |  |
| Composite values |  |  |  |  |  |
| Invalid token/group mix |  |  |  |  |  |
| Unknown future types |  |  |  |  |  |

Для каждого `No` должно быть одно из трех решений:

- Reject with diagnostic.
- Preserve opaquely.
- Import lossy only under explicit option.

### Рекомендуемая политика

```ts
fromDTCG(document, {
  strict: true,
  unknownTypes: 'preserve',
  unknownExtensions: 'preserve',
  lossy: 'error',
})
```

По умолчанию никакая неизвестная metadata не должна молча исчезать. Это позволит ThemeOn пережить новые версии DTCG без немедленного релиза core.

### Round-trip tests

Добавить три уровня:

1. `DTCG → IR → DTCG` — semantic equality.
2. `ThemeOn DSL → IR → DTCG → IR` — domain equality.
3. Набор официальных и внешних fixtures — expected diagnostics.

Property-based генератор должен строить валидные вложенные группы, aliases, type inheritance и расширения, затем проверять round trip.

## Token taxonomy

Модель `ref → sys → comp` соответствует распространенной трехуровневой схеме primitive → semantic → component. Figma описывает именно primitive, semantic и component-specific tokens, при этом primitive служат foundation/reference layer, а semantic несут назначение. [help.figma](https://help.figma.com/hc/en-us/articles/18490793776023-Update-1-Tokens-variables-and-styles)

Однако эти уровни следует трактовать как **policy ThemeOn**, а не как семантику групп DTCG. Спецификация прямо указывает, что инструменты не должны выводить тип или назначение токена из группы, в которой он находится. [designtokens](https://www.designtokens.org/TR/2025.10/format/)

Рекомендуемые dependency rules:

```text
ref  → literal only
sys  → ref | sys where explicitly allowed
comp → sys | comp-local alias
```

Я бы запретил:

- `ref → sys`
- `sys → comp`
- Межкомпонентные ссылки `comp.button → comp.input`
- Использование primitive токена компонентом без escape hatch
- Циклы даже при совпадающих итоговых CSS values

Исключения должны объявляться через policy и попадать в diagnostics, а не быть неявно разрешенными resolver.

## Component tokens

Не стоит создавать component tokens для каждого возможного CSS-свойства. Они нужны как стабильные override points только там, где компонент действительно имеет собственную семантику.

Хорошая модель:

```text
comp.button.primary.container.background.rest
comp.button.primary.container.background.hover
comp.button.primary.label.color.rest
comp.button.primary.focus.ring
```

Но физическое CSS-имя можно сделать короче через naming strategy. Длинный domain path полезен для tooling и документации, а не обязательно должен один к одному становиться custom property.

## Diagnostics

`ThemeonError` с кодами — хорошая основа, но компилятору нужна единая структурированная diagnostic model для core, CLI, Vite, Nuxt и IDE.

```ts
export interface Diagnostic {
  readonly code: string
  readonly severity: 'error' | 'warning' | 'info'
  readonly message: string
  readonly path?: readonly string[]
  readonly source?: SourceLocation
  readonly related?: readonly RelatedLocation[]
  readonly hint?: string
  readonly documentation?: string
}
```

Примеры стабильных кодов:

```text
THEMEON_REF_NOT_FOUND
THEMEON_REF_CYCLE
THEMEON_NAME_COLLISION
THEMEON_DTCG_LOSSY_IMPORT
THEMEON_DTCG_UNKNOWN_TYPE
THEMEON_SYS_LITERAL_FORBIDDEN
THEMEON_COMPONENT_USES_PRIMITIVE
THEMEON_CONTRAST_WCAG_AA
THEMEON_CONTRAST_APCA_ADVISORY
THEMEON_PATCH_UNSAFE_VALUE
```

CLI должен иметь `--format pretty|json|github`, чтобы diagnostics можно было использовать из CI, IDE и других агентов без parsing human-readable текста.

## Accessibility

Сейчас `@themeon/colors` позиционирует APCA как contrast gate. Это полезная экспериментальная метрика, но **APCA нельзя использовать как единственный compliance gate**. [Colors manifest](https://github.com/axiomasoft/themeon/blob/main/packages/colors/package.json)

Действующая WCAG 2.2 требует 4.5:1 для обычного текста, 3:1 для крупного текста и 3:1 для необходимых UI components и graphical objects. [w3](https://www.w3.org/TR/WCAG22/)

WCAG 3 в 2026 году остается Working Draft, причем актуальный draft говорит, что конкретная contrast measure еще определяется. [w3](https://www.w3.org/TR/wcag-3.0/)

### Новая модель

```ts
checkContrast({
  foreground,
  background,
  policies: [
    wcag22Text({ level: 'AA', size: 16, weight: 400 }),
    wcag22NonText(),
    apca({ mode: 'advisory' }),
  ],
})
```

Результат не должен быть одним boolean:

```ts
interface ContrastResult {
  wcag22?: {
    ratio: number
    threshold: number
    pass: boolean
  }
  apca?: {
    lc: number
    threshold?: number
    pass?: boolean
    experimental: true
  }
}
```

CLI должен различать:

- Normative failure.
- Experimental/advisory failure.
- Unsupported context.
- Неопределимый фон, например alpha или gradient.

## CSS foundation

`@themeon/css` концептуально не надо превращать в UI framework. Его роль — layers, reset, base styles и композиционные primitives.

Вместо новых пакетов лучше дать granular entrypoints:

```text
@themeon/css/layers.css
@themeon/css/reset.css
@themeon/css/base.css
@themeon/css/layout.css
@themeon/css/components.css
@themeon/css/all.css
```

Необходимо формально зафиксировать layer order:

```css
@layer themeon.reset,
       themeon.base,
       themeon.layout,
       themeon.components,
       app.components,
       app.utilities,
       app.overrides;
```

Потребителю должна быть предоставлена возможность импортировать только reset или layout. Отдельно проверьте tree-shaking и package `sideEffects` для CSS entrypoints: CSS нельзя случайно удалить из consumer build из-за некорректного `sideEffects: false`.

## Tailwind bridge

Tailwind v4 использует `@theme` variables одновременно как design tokens и как инструкцию для генерации utility classes. Официальная документация отдельно рекомендует `@theme inline`, когда theme variable ссылается на другую переменную. [tailwindcss](https://tailwindcss.com/docs/theme)

Текущий подход ThemeOn с bridge через `@theme inline` выглядит оправданным, но его нужно защитить compile-level contract tests:

- Light/dark theme.
- Три и более `data-theme`.
- Переключение темы после загрузки.
- Nested theme scope.
- Shadow DOM consumer.
- Utility output после minification.
- Tailwind minor upgrades.
- Reference chain длиной больше единицы.
- Fallback custom property.
- Alpha modifiers.

Полезно предоставить стратегии:

```ts
tailwindBridge(resolved, {
  mode: 'inline-reference' | 'theme-variable' | 'static',
})
```

Не следует обещать, что одна стратегия корректна для всех потребителей Tailwind.

## Framework adapters

`@themeon/naive` правильно построен как отдельный пакет с peer dependencies на Naive UI и Vue. Он зависит от core и colors, а не наоборот. [Naive manifest](https://github.com/axiomasoft/themeon/blob/main/packages/naive/package.json)

Пока существует один полноценный UI-library adapter, создавать `@themeon/adapter-kit` рано. Но внутренний контракт уже можно сформулировать:

```ts
export interface ThemeAdapter<
  TOptions,
  TResult,
  TCapabilities extends AdapterCapabilities,
> {
  readonly name: string
  readonly capabilities: TCapabilities

  adapt(
    theme: CompiledTheme,
    options: TOptions,
  ): AdapterResult<TResult>
}
```

`AdapterResult` должен содержать не только output:

```ts
interface AdapterResult<T> {
  value: T
  consumed: readonly TokenId[]
  ignored: readonly TokenId[]
  diagnostics: readonly Diagnostic[]
}
```

Тогда можно тестировать coverage адаптера: какие semantic roles он действительно перенес, какие проигнорировал и какие вычислил самостоятельно.

## Vue и runtime

Vue package имеет отдельный anti-FOUC entrypoint, что является хорошей границей: основной composable не обязан тащить генератор head-script. [Vue manifest](https://github.com/axiomasoft/themeon/blob/main/packages/vue/package.json)

В runtime-контракте необходимо явно проверить:

- SSR без `window` и `document`.
- Storage throwing `SecurityError`.
- Storage disabled.
- Неизвестное persisted theme name.
- Несколько Vue applications на странице.
- Несколько scoped theme roots.
- `matchMedia` без `addEventListener`.
- Cross-tab synchronization.
- Cleanup listeners при unmount.
- Hydration при несовпадении server/client preference.
- CSP nonce и hash для anti-FOUC script.
- Повторная инициализация без дублирования watchers.
- Browser back-forward cache.
- Forced-colors mode.
- No-JS fallback.

Anti-FOUC generator должен возвращать не только строку:

```ts
interface AntiFoucArtifact {
  code: string
  hash: string
  minified: string
  storageKey: string
  attributes: readonly string[]
}
```

Это упростит строгий CSP в Laravel и Nuxt.

## Laravel integration

Для Laravel правильная точка интеграции — `@themeon/vite`, а не отдельная PHP-реализация resolver. Один и тот же TypeScript compiler должен использоваться и Nuxt, и Laravel/Vite, чтобы не возникали два источника истины.

Полезное развитие:

- `themeon build --manifest`.
- Vite virtual module с typed token names.
- PHP-readable manifest только как скомпилированный artifact.
- Blade helper для выбора theme attribute — только после реального потребителя.
- CSP hash export для anti-FOUC script.
- Watch mode с atomic file replacement.
- Laravel Mix не поддерживать без отдельного запроса.

Composer-пакет сейчас не нужен; существующий trigger-gated подход roadmap здесь правильный. [ROADMAP](https://github.com/axiomasoft/themeon/blob/main/ROADMAP.md)

## Multi-tenant patches

Tenant patching — одна из наиболее ценных и одновременно наиболее рискованных возможностей. Core уже экспортирует patch application, serializer, allowed tenant types и JSON Schema. [Core index](https://github.com/axiomasoft/themeon/blob/main/packages/core/src/index.ts)

Нужно провести отдельный security audit:

- Prototype pollution через `__proto__`, `prototype`, `constructor`.
- Чрезмерно глубокие объекты.
- Огромное число ключей.
- Очень длинные CSS values.
- `url()` и внешние resources.
- `@import`.
- Незакрытые строки и комментарии.
- CSS custom-property breakout.
- Unicode control characters.
- Invalid surrogate sequences.
- Alias cycles, возникшие после patch.
- Обращение tenant patch к primitive/internal tokens.
- Patch одного tenant поверх результата другого tenant.
- Schema и runtime validator divergence.

Для SaaS рекомендую policy levels:

```ts
tenantThemeSchema({
  policy: 'branding' | 'extended' | 'trusted',
})
```

`branding` разрешает только заранее объявленные semantic colors, fonts, radii и логотипы. `extended` открывает больше токенов, а `trusted` предназначен для конфигурации владельца системы, не для пользовательского ввода.

## Тестовая модель

### Coverage gates

Сейчас корневой Vitest config включает V8 coverage provider, но не задает thresholds и даже не включает coverage в основной CI-команде. [Vitest config](https://github.com/axiomasoft/themeon/blob/main/vitest.config.ts)

Не нужно гнаться за 100% по всему монорепозиторию. Введите риск-ориентированные пороги:

| Подсистема | Lines | Branches |
|---|---:|---:|
| Resolver/graph | 95% | 95% |
| Naming | 100% | 100% |
| DTCG conversion | 95% | 95% |
| Tenant patches | 95% | 95% |
| Serialization | 95% | 90% |
| Framework glue | 80% | 75% |
| CLI presentation | 70% | 65% |

Порог должен применяться к измененным критическим файлам или к пакету, иначе монорепозиторный global threshold будет мешать добавлять новые пакеты.

### Property-based tests

Добавьте `fast-check` для:

- Случайных token trees.
- Произвольной глубины aliases.
- Циклов.
- Name collisions после kebab normalization.
- Unicode token names.
- DTCG round trips.
- Theme patches.
- Tenant patch schemas.
- CSS serialization determinism.
- Порядка ключей входного объекта.
- Equivalent themes with different object insertion order.

Ключевые properties:

```text
resolve(resolveInput) is deterministic
serialize(theme) is deterministic
fromDTCG(toDTCG(theme)) preserves semantics
clearTheme(applyTheme(theme)) restores previous state
naming(pathA) !== naming(pathB) for valid distinct public paths
patch(base, empty) = base
patch(patch(base, A), B) respects documented precedence
```

### Mutation tests

Mutation testing особенно полезно для:

- Cycle detection.
- Name collision detection.
- Contrast thresholds.
- Patch allowlists.
- DTCG strict validation.
- Theme fallback selection.

Запускать его можно nightly, а не на каждый pull request.

### Consumer tests

`publint` и Are The Types Wrong уже включены, но следует добавить установку реально упакованных tarballs:

```text
pnpm pack each package
  → create temporary consumer
  → install from tarballs
  → typecheck
  → build
  → SSR import
  → browser import
```

Матрица consumers:

- Plain TypeScript ESM.
- Vite.
- Vue.
- Nuxt SSR.
- Laravel Vite.
- Tailwind v4.
- Node without DOM.
- Workspace with `moduleResolution: bundler`.
- Workspace with `moduleResolution: nodenext`.

Проверка через `workspace:*` не обнаруживает часть проблем опубликованного tarball.

### Browser matrix

Текущий CI устанавливает Chromium для integration testing. [CI workflow](https://github.com/axiomasoft/themeon/blob/main/.github/workflows/ci.yml)

Fast/browser tests достаточно выполнять в Chromium, но theme persistence, anti-FOUC и media queries стоит периодически проверять также в Firefox и WebKit. Полную матрицу можно запускать nightly или перед release, чтобы не утроить длительность каждого PR.

## API stability

API snapshot защищает список exports, но не все TypeScript breaking changes. Например, narrowing generic constraint или превращение optional property в required может сломать потребителя, не изменив export names.

Добавьте API report:

```text
etc/api/
├── core.api.md
├── colors.api.md
├── vue.api.md
└── naive.api.md
```

Подойдет API Extractor либо собственный TypeScript declaration snapshot поверх уже создаваемых `.d.ts`. На PR должно быть видно, какие generic signatures и union members изменились.

Отдельно заведите compatibility fixtures для типов:

```ts
expectTypeOf(defineTheme(...)).toMatchTypeOf<Expected>()
// @ts-expect-error — component cannot reference forbidden primitive
```

## Performance

Для token compiler нужны отдельные benchmarks, потому что обычные unit tests не обнаружат квадратичный resolver или чрезмерное создание объектов.

Минимальные сценарии:

| Сценарий | Размер |
|---|---:|
| Small application | 200 tokens, 2 themes |
| Medium design system | 2,000 tokens, 4 themes |
| Large multi-brand | 10,000 tokens, 20 themes |
| Deep alias chain | 1,000 references |
| Wide component layer | 5,000 component tokens |
| Tenant patch | 500 overrides |

Измерять:

- Parse time.
- Graph build.
- Resolve time.
- CSS serialization.
- DTCG round trip.
- Peak memory.
- Vite cold start.
- HMR update.
- Runtime application.
- Output CSS size.
- Gzip size.

В CI лучше проверять не абсолютные миллисекунды, а грубые regression budgets, например не более 20–30% против сохраненного baseline.

## Release pipeline

Текущий release workflow использует `NPM_TOKEN` и не запрашивает `id-token: write`. [Release workflow](https://github.com/axiomasoft/themeon/blob/main/.github/workflows/release.yml)

npm trusted publishing позволяет публиковать из GitHub Actions через OIDC без долгоживущего npm token и автоматически генерирует provenance для публичного пакета из публичного репозитория. [docs.npmjs](https://docs.npmjs.com/trusted-publishers/)

### Рекомендуемый workflow

- Перейти на npm trusted publisher.
- Добавить `id-token: write`.
- После успешного перехода запретить token-based publishing.
- Добавить explicit minimal permissions.
- Pin actions по immutable commit SHA.
- Повторно выполнить полный verify перед publish.
- Публиковать только из protected environment.
- Проверять чистоту git tree после build.
- Сохранять tarballs как release artifacts.
- Проверять `npm audit signatures`.
- Генерировать SBOM.
- Делать dry-run package manifest diff.

Сейчас release job выполняет install и build, но не запускает lint, typecheck, unit, integration и `check:pack`; он полагается на независимый CI run того же commit. [Release workflow](https://github.com/axiomasoft/themeon/blob/main/.github/workflows/release.yml)

Лучше выделить reusable workflow:

```text
verify:
  install
  build
  lint
  typecheck
  unit
  integration-fast
  check-pack

release:
  needs: verify
  integration-slow
  changesets publish
```

## Сравнение подходов

| Проект | Что заимствовать | Что не копировать |
|---|---|---|
| Style Dictionary | Staged pipeline, preprocessors, transforms, formats | Global mutable registration и config-heavy UX |
| Vanilla Extract | Typed theme contract и полноту реализации темы | Привязку authoring model к CSS-in-TS |
| Panda CSS | Semantic tokens и typed condition mappings | Полную atomic-CSS/codegen платформу |
| Tailwind v4 | Theme-variable bridge и utility interoperability | Роль основного token source |
| DTCG | Interchange format и metadata semantics | Использование JSON как обязательного authoring UX |
| Nuxt module starter | Fixture E2E и packed-package tests | Nuxt-specific архитектуру core |

Vanilla Extract полезен именно идеей contract-first: `createThemeContract` отделяет структуру темы от реализаций, а каждая реализация должна заполнить контракт полностью. [vanilla-extract](https://vanilla-extract.style/documentation/api/create-theme-contract/)

Panda CSS полезен разделением raw и semantic tokens, а также condition-based values; это можно использовать как референс для responsive/theme conditions, не превращая ThemeOn в CSS framework. [panda-css](https://panda-css.com/docs/theming/tokens)

## Что не делать

- Не переносить весь core на Style Dictionary.
- Не делать DTCG JSON единственным authoring format.
- Не превращать `@themeon/css` в компонентную библиотеку.
- Не выпускать пять новых framework adapters без потребителей.
- Не дробить core на множество npm-пакетов до стабилизации внутренних границ.
- Не считать APCA заменой WCAG.
- Не разрешать plugin глобально мутировать registry.
- Не разрешать formatters изменять resolved graph.
- Не делать network access частью обычной сборки.
- Не принимать arbitrary tenant CSS values без threat model.
- Не обещать стабильность каждого exported helper до 1.0.
- Не добавлять component tokens только ради полноты таблицы.
- Не генерировать responsive значения скрыто без отображения в diagnostics.
- Не поддерживать CommonJS, если нет подтвержденного потребителя.
- Не добавлять React/Svelte только ради списка integrations.
