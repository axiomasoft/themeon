# @themeon/tailwind

Tailwind v4 CSS-first bridge for ThemeOn: `tailwindBridge(resolved)` generates a
`@theme reference { … }` block (literal values) from a resolved ThemeOn theme, so
Tailwind generates utilities under the same class names (`bg-action-primary`, `p-md`, …)
without ever declaring ThemeOn's own CSS custom properties itself — runtime `[data-theme]`
swaps from `tokens.css` reach the generated utilities through their `var(--x, <literal>)`
fallback slot.

## Why `@theme reference`, not `@theme inline`

Earlier versions of this bridge used a self-referential `@theme inline { --x: var(--x) }`
mapping. That form breaks under Tailwind 4.3.2 in two ways, both reproduced by real
compilation + Chromium (`findings/P8-tailwind-bridge-form.md`):

- **Cycle.** Whenever `tokens.css` (which declares the real `--x` value) is parsed before
  Tailwind's own `@theme` block — any import order other than
  `tailwindcss → bridge → tokens` — Tailwind's tree-shaker sees the utility reference
  `var(--x)`, marks `--x` as used, and re-declares it in `:root, :host` with its own
  (self-referential) value: `--x: var(--x)`. That's an invalid-at-computed-value-time
  cycle — the variable, and every rule using it, resolves to nothing.
- **`--breakpoint-*` in `@media`.** Tailwind substitutes a breakpoint's value as a literal
  **string** into `@media (width >= …)` — never through a `var()` lookup. A self-referential
  `--breakpoint-md: var(--breakpoint-md)` therefore produces `@media (width >= var(--breakpoint-md))`,
  which is invalid CSS (`var()` isn't allowed in a media condition) and gets silently
  dropped by the browser — every `md:`/`lg:` utility becomes dead.

`@theme reference` sidesteps both: Tailwind **never** emits the referenced variables into
`:root, :host` (confirmed against the 4.3.2 source, since this option is undocumented), so
there is nothing left to fight over import order. Utilities get `var(--x, <literal>)` — the
runtime `[data-theme]` value from `tokens.css` wins when present, and the baked-in literal
is a graceful fallback if `tokens.css` isn't loaded. `--breakpoint-*` is emitted as a bare
literal (never `var()`) for the reason above; `--shadow-*` is the one exception kept as
`var(--shadow-*)`, because Tailwind parses shadow values at build time and a literal would
bake in the light-theme shadow permanently, breaking the dark-theme swap.

## Quickstart

```css
/* app.css */
@import "tailwindcss";
@import "./theme-bridge.css"; /* generated by tailwindBridge — @theme reference block */
@import "./tokens.css";        /* @themeon/core serializeThemeCss output — the values */
```

```ts
import { resolveTheme } from '@themeon/core'
import { tailwindBridge } from '@themeon/tailwind'
import { theme } from './theme.config'

const resolved = resolveTheme(theme)
const bridgeCss = tailwindBridge(resolved)
// write bridgeCss to ./theme-bridge.css (build step — see `themeon build --tailwind`, P4.4)
```

The actual runtime values (light base + `[data-theme="…"]` patches) live in `tokens.css`,
produced separately by `serializeThemeCss` (`@themeon/core`). Import order between
`bridge.css`, `tokens.css` and `tailwindcss` no longer matters — `@theme reference` never
emits, so there's nothing for load order to override.

## Limitation: breakpoints are not runtime-themeable

Tailwind substitutes `--breakpoint-*` as a literal string directly into `@media (width >= …)`
at build time — this is a Tailwind constraint, not a ThemeOn one. Switching breakpoints on
the fly via `[data-theme]` is not possible with any bridge form; `--breakpoint-*` still
lives in `tokens.css` (for `@custom-media` and hand-written CSS), but it does not drive
`md:`/`lg:` utilities at runtime.

## Options

```ts
export interface TailwindBridgeOptions {
  /** 'all' = base tokens ∪ all theme patches (union of names); 'base' = only base. Default 'all'. */
  include?: 'all' | 'base'
  /** Restrict emitted namespaces (subset of TAILWIND_NAMESPACES). Default: all of them. */
  namespaces?: readonly string[]
  /** Emit leading "generated" banner comment. Default true. */
  banner?: boolean
}
```

| Option | Default | Effect |
|:--|:--|:--|
| `include` | `'all'` | `'all'` unions var names across the base and every theme patch (a theme may introduce a var absent from the base). `'base'` restricts to base-only names. |
| `namespaces` | `TAILWIND_NAMESPACES` | Subset filter — pass a smaller list to emit fewer namespaces (e.g. only `['color']`). |
| `banner` | `true` | Prepends a one-line "generated" comment; set `false` for byte-exact diffing in tests/tooling. |

## Namespace filter (`TAILWIND_NAMESPACES`)

Only ThemeOn vars whose namespace Tailwind v4 recognises for utility generation are
emitted: `color`, `font-weight`, `font`, `text`, `tracking`, `leading`, `breakpoint`,
`spacing`, `radius`, `shadow`, `ease`. ThemeOn extensions with no Tailwind counterpart —
`gradient`, `z`, `duration` — are intentionally excluded; including them would only
produce dead `@theme reference` declarations Tailwind ignores.

Double-dash line-height companion variables (e.g. `--text-2xl--line-height`, emitted
alongside `--text-2xl` by the naming engine) are **included** — Tailwind v4's `--text-*`
utilities only bundle a `line-height` declaration when this companion is present in
`@theme`; omitting it silently drops leading from every `text-*` utility (R-11 §3).

## Naming

`tailwindBridge` does not name anything — every var name comes straight out of
`ResolvedTheme` (ThemeOn's single naming engine, applied once in the resolver). This
package only filters and formats; there is no second kebab/namespace transform here.
