# @themeon/tailwind

Tailwind v4 CSS-first bridge for ThemeOn: `tailwindBridge(resolved)` generates a
**self-referential** `@theme inline { … }` block from a resolved ThemeOn theme, so
runtime `[data-theme]` swaps reach the utilities Tailwind generates from it — without a
rebuild.

## Why `@theme inline`, not plain `@theme`

Tailwind v4 only generates utilities from variables declared inside `@theme`. A plain
(non-inline) `@theme` declaration creates a **global** `:root` custom property whose value
is resolved once, in the `:root` scope — a later `[data-theme="dark"] { --color-x: … }`
override does **not** reach utilities built from it, because the utility's own declaration
already captured the `:root` value.

`@theme inline` instead makes Tailwind embed `var(--x)` directly into each generated
utility. The variable is then re-resolved at the point of use, in whatever scope applies —
so a `[data-theme="dark"]` ancestor override reaches the utility exactly like any other CSS
custom property. `@theme inline` is therefore **mandatory**, not a style choice: any
ThemeOn var routed to Tailwind through this bridge must go through it.

## Quickstart

```css
/* app.css */
@import "tailwindcss";
@import "./theme-bridge.css"; /* generated by tailwindBridge — @theme inline block */
@import "./tokens.css";        /* @themeon/core serializeThemeCss output — the values */
```

```ts
import { resolveTheme } from '@themeon/core'
import { tailwindBridge } from '@themeon/tailwind'
import { theme } from './theme.config'

const resolved = resolveTheme(theme)
const bridgeCss = tailwindBridge(resolved)
// write bridgeCss to ./theme-bridge.css (build step — see `themeon build --tailwind`, P4.4)
```

`tailwindBridge` never emits values — only `var()` references. The actual values (light
base + `[data-theme="…"]` patches) live in `tokens.css`, produced separately by
`serializeThemeCss` (`@themeon/core`). Import order matters: `bridge.css` before
`tokens.css`, both after `tailwindcss`.

## Options

```ts
export interface TailwindBridgeOptions {
  /** 'all' = base tokens ∪ all theme patches (union of names); 'base' = only base. Default 'all'. */
  include?: 'all' | 'base'
  /** Restrict emitted namespaces (subset of TAILWIND_NAMESPACES). Default: all of them. */
  namespaces?: readonly string[]
  /** Emit leading "generated" banner comment. Default true. */
  banner?: boolean
}
```

| Option | Default | Effect |
|:--|:--|:--|
| `include` | `'all'` | `'all'` unions var names across the base and every theme patch (a theme may introduce a var absent from the base). `'base'` restricts to base-only names. |
| `namespaces` | `TAILWIND_NAMESPACES` | Subset filter — pass a smaller list to emit fewer namespaces (e.g. only `['color']`). |
| `banner` | `true` | Prepends a one-line "generated" comment; set `false` for byte-exact diffing in tests/tooling. |

## Namespace filter (`TAILWIND_NAMESPACES`)

Only ThemeOn vars whose namespace Tailwind v4 recognises for utility generation are
emitted: `color`, `font-weight`, `font`, `text`, `tracking`, `leading`, `breakpoint`,
`spacing`, `radius`, `shadow`, `ease`. ThemeOn extensions with no Tailwind counterpart —
`gradient`, `z`, `duration` — are intentionally excluded; including them would only
produce dead `@theme inline` declarations Tailwind ignores.

Double-dash companion variables (e.g. `--text-2xl--line-height`, emitted alongside
`--text-2xl` by the naming engine) are excluded for the same reason.

## Naming

`tailwindBridge` does not name anything — every var name comes straight out of
`ResolvedTheme` (ThemeOn's single naming engine, applied once in the resolver). This
package only filters and formats; there is no second kebab/namespace transform here.
