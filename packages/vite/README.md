# @themeon/vite

Vite plugin for ThemeOn: a `virtual:themeon.css` module (theme CSS as an importable virtual
module, no build step of your own) with HMR (`hotUpdate`) and an optional generated anti-FOUC
script — for Laravel/plain (non-Nuxt) projects. Same pattern as
[UnoCSS's Vite integration](https://github.com/unocss/unocss).

> Nuxt has its own channel — [`@themeon/nuxt`](https://github.com/themeon/themeon/tree/main/packages/nuxt).
> This plugin is for everything else that runs on Vite: Laravel + Vite, plain Vue/vanilla SPAs.

> **Status: pre-1.0 — the API may change.**

## Install

```sh
pnpm add @themeon/vite @themeon/core vite
```

ESM-only, Node `>= 22.18`, `vite: ^7 || ^8` (peer). Does **not** require `vue` in your
dependency graph — the anti-FOUC script is generated by a pure subpath
(`@themeon/vue/anti-fouc`) with zero Vue imports.

## Quickstart

The only supported connection is a JS/TS import — **not** a CSS `@import` (see "Why not CSS
`@import`" below):

```ts
// vite.config.ts
import { defineConfig } from 'vite'
import { themeon } from '@themeon/vite'
import { theme } from './theme.config'

export default defineConfig({
  plugins: [
    themeon({
      theme,
      tokensFiles: ['./theme.config.ts'],
      injectFouc: true, // inserts the anti-FOUC script into index.html
    }),
  ],
})
```

```ts
// src/main.ts
import 'virtual:themeon.css'
import '@themeon/css/index.css'
```

**Note:** importing `theme` statically into `vite.config.ts` (as above) makes the theme file a
Vite *config dependency* — editing it restarts the whole dev server (a full page reload), not a
live HMR update. That's the simplest setup and fine for most projects. For live HMR (edit the
file, styles update in place, no reload), see "Live HMR" below.

## Live HMR

For the theme file to update live instead of triggering a full server restart, it must **not**
be a config dependency — load it with a factory that reads the file at request time instead of a
static `import`. [`jiti`](https://github.com/unjs/jiti) works well for a `.ts` theme file (fresh
read on every call, no module-cache staleness):

```sh
pnpm add -D jiti
```

```ts
// vite.config.ts
import { defineConfig } from 'vite'
import { createJiti } from 'jiti'
import { themeon } from '@themeon/vite'

const jiti = () => createJiti(import.meta.url, { moduleCache: false, fsCache: false })

export default defineConfig({
  plugins: [
    themeon({
      theme: async () => (await jiti().import('./theme.config.ts')).theme,
      tokensFiles: ['./theme.config.ts'],
      injectFouc: true,
    }),
  ],
})
```

`src/main.ts` stays the same (`import 'virtual:themeon.css'`).

## Laravel + Vite

ThemeOn ships no framework glue for Laravel — Laravel projects consume the plugin exactly
like any other Vite project, through `vite.config.js`:

```js
// vite.config.js
import laravel from 'laravel-vite-plugin'
import { defineConfig } from 'vite'
import { themeon } from '@themeon/vite'
import { theme } from './resources/theme.config'

export default defineConfig({
  plugins: [
    laravel({ input: ['resources/css/app.css', 'resources/js/app.js'], refresh: true }),
    themeon({ theme, tokensFiles: ['./resources/theme.config.ts'], injectFouc: true }),
  ],
})
```

```js
// resources/js/app.js
import 'virtual:themeon.css'
```

`resources/css/app.css` is left untouched — **do not** add `@import 'virtual:themeon.css'`
there, it never works (see "Why not CSS `@import`"). In hot mode Laravel's `@vite` directive
emits a `<script type="module">` for the JS entry, and Vite's dev client injects the theme CSS
as a `<style>` tag; in a production build, Laravel emits `<link rel=stylesheet>` for the CSS
chunks that came out of the JS entry — no extra wiring needed.

If your Laravel setup has **no JS entry at all** (pure Blade + CSS), use the `cssImport` option
instead — see "CSS-only projects" below.

`injectFouc: true` inserts the anti-FOUC script into the page `<head>` via
`transformIndexHtml` — but Laravel serves Blade templates, not `index.html`, so
`transformIndexHtml` never runs in a classic Laravel setup. Either inline the same script
yourself in the Blade layout using `@themeon/vue/anti-fouc`'s `themeInitScript()`, or (for a
Vue/Inertia SPA shell that does go through Vite's `index.html`) rely on `injectFouc` as shown
above.

## Plain / vanilla

Any Vite project — no framework at all:

```ts
// src/main.ts
import 'virtual:themeon.css'
```

No `useTheme()` composable here — that lives in `@themeon/vue`. This plugin only ships CSS;
runtime theme switching is up to you (toggle the `data-theme` attribute, or bring in
`@themeon/vue` for the ready-made composable).

## CSS-only projects (no JS entry)

If your project has no JS/TS entry point to `import` from (pure CSS entry, e.g. a Blade layout
with only `resources/css/app.css`), enable `cssImport`: the plugin writes the theme's CSS to a
real file on disk and aliases `virtualId` to it, so the documented
`@import 'virtual:themeon.css'` syntax works — it now resolves to an ordinary file instead of a
virtual module (virtual modules can't be resolved by CSS `@import`, see below):

```ts
// vite.config.ts
themeon({
  theme,
  tokensFiles: ['./theme.config.ts'],
  cssImport: true, // writes `.themeon/theme.css`, aliases virtual:themeon.css → that file
})
```

```css
/* resources/css/app.css */
@import 'virtual:themeon.css';
@import './other.css';
```

Add `.themeon/` to `.gitignore` — it's a generated artifact, rewritten on every theme change.
HMR here is driven entirely by Vite's own filesystem watcher (no custom `hot.send` needed): it
sees the real file change and updates the CSS module that imports it. This is not a replacement
for the canonical JS-import channel above — it's an additional option for CSS-first setups.

## Why not CSS `@import`?

`@import 'virtual:themeon.css'` **cannot** work from CSS — only from JS/TS. Vite's CSS pipeline
resolves `@import` through `postcss-import`, which uses its own filesystem-only resolver; plugin
`resolveId`/`load` hooks are never consulted for `@import` targets in CSS files, virtual or not.
This isn't a bug in this plugin — the same limitation applies to
[UnoCSS](https://github.com/unocss/unocss/issues/3853), whose `virtual:uno.css` module has the
identical restriction and is documented as JS-import-only. The `cssImport` option above works
around this by aliasing the virtual id to a real file instead.

## Options (`ThemeonViteOptions`)

| Option | Type | Default | Notes |
|:--|:--|:--|:--|
| `theme` | `ThemeDefinition \| (() => ThemeDefinition \| Promise<ThemeDefinition>)` | — | **Required.** A factory is re-invoked on every `load()`, so it always reflects the current on-disk state during HMR. |
| `tokensFiles` | `string[]` | `[]` | Paths (relative to project root, or absolute) that trigger HMR of the virtual module when changed. Without it, HMR is inactive — restart Vite to see theme changes. |
| `resolve` | `ResolveOptions` (core) | — | Passed through to `resolveTheme` as-is. |
| `serialize` | `SerializeCssOptions` (core) | — | Passed through to `serializeThemeCss` as-is. |
| `virtualId` | `string` | `'virtual:themeon.css'` | Public id of the virtual module. |
| `cssImport` | `boolean \| { file?: string }` | `false` | CSS-first channel for projects with no JS entry — writes the theme CSS to a real file and aliases `virtualId` to it (see "CSS-only projects"). `true` uses `.themeon/theme.css`; `{ file }` overrides the path (relative to project root). |
| `injectFouc` | `boolean \| ThemeInitScriptOptions` | `false` | Inserts the generated anti-FOUC script (`@themeon/vue/anti-fouc`) into `index.html` via `transformIndexHtml`, `head-prepend`. |

## How HMR works

The plugin implements the `hotUpdate` hook (Vite Environment API — the modern replacement for
the deprecated `handleHotUpdate`): when a changed file matches `tokensFiles`, it invalidates the
virtual module in the environment's module graph and returns `[mod]`, letting Vite build and
send the update payload itself. This is the only form that's robust to how Vite normalizes
`\0`-prefixed virtual module URLs for the dev client — a hand-rolled `hot.send()` call, no matter
how the path is derived, ends up not matching the client's internal HMR module map and silently
does nothing. If the file isn't in `tokensFiles`, the hook is a no-op and Vite's default handling
proceeds unaffected.
